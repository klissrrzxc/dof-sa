# Развёртывание Supabase + Vercel

Деплой в этой поставке не выполнялся. Не применять SQL к чужому действующему проекту: обнаруженный подключённый Supabase используется другим приложением; отдельный проект FMS не выбран.

1. Владелец создаёт отдельный Supabase-проект или явно выбирает предназначенный для FMS. Сначала проверить существующую схему/миграции и сделать резервную копию. Новый проект рекомендуется для исключения конфликта имён.
2. `pnpm exec supabase link` и `pnpm exec supabase db push` после просмотра `--help` и SQL-ревью. Применяются миграции из `supabase/migrations`. Выполнить Database/Security advisors и исправить замечания. Облачные advisors здесь не запускались: целевой проект не подключён.
3. В Auth отключить public signup и anonymous sign-ins; включить TOTP enrollment/verification. Пароль от 12 символов; включить подтверждения email и защиту изменения пароля. Проверить rate limits входа/OTP, настроить production SMTP и допустимый срок приглашения (например, 1 час согласно локальному конфигу).
4. Настроить Site URL на HTTPS origin Vercel, Redirect URLs — точный `/auth/confirm`. Invite email template:

```html
<a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=invite">Принять персональное приглашение</a>
```

Не использовать шаблон, который отдаёт access token в URL-фрагменте: серверный обработчик рассчитан на `token_hash`. Ссылка одноразовая, проверяется Supabase Auth. Локальный SMTP смотрят через Inbucket локального стека.

5. Через Dashboard пригласить первого владельца, скопировать его Auth UUID. Заполнить `supabase/bootstrap-admin.sql` локально фактическими RP-реквизитами и выполнить от trusted owner. Не коммитить личные значения. Принять приглашение, установить пароль, подключить TOTP. Скрипт создаёт системного администратора, без финансовых прав и без начальных денег.
6. Импортировать GitHub-репозиторий `klissrrzxc/dof-sa` в Vercel. Framework Next.js; Node 24; Root Directory — корень. Build `pnpm build`, install `pnpm install --frozen-lockfile`. Добавить переменные из `.env.example` в защищённые настройки Vercel, раздельно Preview и Production. Service role только server env.
7. APP_ORIGIN = точный HTTPS origin. Не открывать тестовый стенд реальным данным; разделить Supabase-проекты Preview и Production. Защитить ветки/production deployment, ограничить сетевой доступ по возможностям тарифа. Настроить Vercel Firewall/rate limits Server Actions, включая приглашения; приложение не имеет распределённого ограничителя для них.
8. До допуска пользователей проверить AAL1/AAL2, отзыв назначения и blocked profile через прямые REST-запросы, закрытый Storage, приглашения, cookie refresh, 403 и отсутствие индексации. Полный live Auth/Storage e2e не заменяется PGlite.

## Что требуется от владельца

- Отдельный Supabase project ref, URL и publishable key; DB-доступ для применения миграций. Не отправлять пароли в чат.
- Server-only service-role key для приглашений; SMTP и шаблон письма.
- Vercel project, домен/HTTPS origin и env-настройки.
- IC-данные, ведомство, должность и Auth UUID первого администратора.
- Утверждённые нормативные формы/классификаторы, RP timezone, реальное основание начального остатка и лимитов.

## Backup / restore

Перед миграциями — Supabase backup/PITR по доступному тарифу, отдельно Auth и Storage. DB dump не содержит байты Storage-объектов: их нужно сохранять отдельно с метаданными и контрольными суммами. Секреты и резервные копии не хранить в Git.

Проверять восстановление в отдельном проекте минимум перед релизом и после изменения финансовой схемы: восстановить БД, Auth mapping, приватные файлы; выполнить SQL-тесты/проверку RLS, проверить авторство и аудит, затем проверить вход и MFA с тестовой учётной записью. Записывать дату, длительность, объём и результат восстановления. Регламент описан, реальная резервная копия/восстановление ещё не выполнялись. RPO/RTO устанавливает владелец.
