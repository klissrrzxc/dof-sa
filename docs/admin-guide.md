# Администратор

Первого администратора назначает владелец БД через ручной bootstrap. Пользователь не может назначить себе роль или активировать себя. Администратор входит с MFA и открывает «Администрирование».

Приглашение требует e-mail, IC имени/фамилии, должности, существующего активного ведомства и роли. Отправка выполняется Supabase Auth Admin API на сервере. Если создание профиля/назначения не удалось, выполняется попытка удаления созданного Auth user; даже при отказе компенсации пользователь без профиля не получает доступа. Такие ошибки проверяются в журнале Auth владельцем. Письмо уже могло быть доставлено, но ссылка не даёт доступа к данным без действующего профиля.

Роль и дополнительные финансовые полномочия разделены. Системный администратор имеет управление пользователями/справочниками и чтение аудита; не имеет согласования финансов, резервирования или исполнения. UI управления отдельными permission grants пока не реализован; не назначать их произвольным SQL без оформленного основания и аудита. Для production требуется отдельный проверенный процесс выдачи/отзыва финансовых разрешений.

Смена назначения отзывает текущие роли и добавляет новую запись с автором и временем, вместе с аудитом. Прежние назначения не удаляются. При увольнении «Заблокировать доступ» немедленно закрывает RLS/SSR и RPC; дополнительно владелец отзывает сессии в Auth, при необходимости блокирует Auth user. Историческое авторство остаётся.

Ведомства сейчас вводятся владельцем при bootstrap и далее контролируемым импортом. Рабочего UI редактирования справочников и экспорта CSV на этом этапе нет. Начальных казначейских остатков не создано. Не использовать исторические числа форумного отчёта как текущий баланс.
