# Фактическое состояние

12.11.2026. Рабочая ветка `codex/fms-foundation`. Проект создан в `klissrrzxc/dof-sa`; репозиторий новостного портала `sann` не изменяется.

## Этап 1

Реализованы Next.js App Router, строгий TypeScript, административный интерфейс, Tailwind, Supabase SSR, proxy обновления cookies, вход/выход, приглашение и установка пароля, TOTP enrollment/challenge, серверные 403/редиректы, динамический закрытый layout. В БД: организации, профили, версионируемые роли/permissions, append-only аудит, настройки, приватный bucket, индексы, RLS и ограниченные RPC. Есть администраторский интерфейс приглашений, смены ролей и блокировки. Финансовые разрешения не следуют из роли администратора.

Проверки: TypeScript и ESLint без ошибок; production build Next.js успешен. SQL-тесты в PGlite проверяют анонимный доступ, межведомственную изоляцию профилей, запрет прямой записи, MFA, самоповышение, отдельные финансовые полномочия, атомарный аудит, блокировку старого JWT. Playwright: 9/9 тестов закрытых маршрутов, заголовков и мобильной страницы входа. Полный пользовательский сценарий с реальным Auth пока не проверен.

Облачный проект `yyoodoxfyiicxgambtbr` подключён 12.11.2026: применены 3 миграции, RLS включён на всех 10 таблицах, bucket приватный. Реальные анонимные REST/RPC-проверки и транзакционный SQL smoke test RLS прошли. Security Advisor без замечаний; недостающие FK-индексы добавлены. См. live-verification.md. Ограничения: реальный вход/SMTP/MFA пока не подтверждены live e2e: Auth-пользователей ещё нет; публичный signup в настройках проекта пока включён и должен быть отключён владельцем. Управление permission grants и справочниками, распределённый rate limit приглашений, отзыв Auth-сессий через приложение пока отсутствуют. До production нужны действия из deployment.md.

## Этап 2 — частично

Реализованы финансовые черновики для финансирования/закупок: создание, сохранение в PostgreSQL, просмотр и редактирование, поиск по назначению, фильтр типа, область видимости ведомства/назначенного сотрудника/отдельного `cases.read_all`, версии, история, аудит. Позиции закупки нормализуются в `procurement_items`; денежные строки и BigInt не теряют точность. Устаревшая версия отклоняется, изменения не перетирают параллельно сохранённую редакцию. Суммы и данные проверяются на сервере и в SQL. Пользователь не может изменить собственника/ведомство через JSON.

Официальная регистрация заблокирована на уровне БД, включая прямой RPC. Черновики не имеют MOF-номера, не считаются утверждённой формой и не создают резервов/платежей. Доход не проходит через фиктивную расходную заявку. Ещё не реализованы: подача по утверждённой форме, принятие/рассмотрение/решения, вложения и их авторизация, классификаторы с нормативной сверкой, удаление незарегистрированного черновика, интерфейс просмотра отдельных исторических редакций (сами immutable snapshots сохраняются в БД).

Общий результат модульных и SQL-проверок: 21/21. Есть проверки чужого UUID, попытки переписать чужой черновик, null/stale version, нормативного запрета подачи, неверных типов JSON, BIGINT overflow, точности выше 2^53, отката закупки при недопустимой позиции.

## Этапы 3–5

Казначейство, документы, отчёты, BBCode, резервирование, платёжные инварианты, конкурентные финансовые транзакции, коррекции, signed URL и CSV ещё не реализованы. Их страницы и кнопки не имитируются: навигация показывает только готовые маршруты из предусмотренных шести модулей. CI, базовые e2e и инструкции развёртывания/backup подготовлены, но этап качества всего MVP ещё не завершён. Нормативные формы требуют ручного подтверждения: обе темы подачи ведут на MOF-REQ-01 вместо указанных в актах BFR-01/PR-01. Условия Definition of Done всего MVP не выполнены.
